In [the previous post](/blog/125b-on-a-4090), I got roughly 100 GB of model
weights serving on a 24 GB RTX 4090 with 64 GB of RAM by spilling experts to
disk. The next question was how much of the remaining wait I could remove.

The changes are now [merged into the fork](https://github.com/jomcgi-org/freetoken-fork/pull/66)
and running on the same machine. On a controlled set of three-turn
conversations, total wall time fell from **369.1 seconds to 252.4 seconds**.
That is **31.6% less waiting**, with the same request bodies, complete answers
and generated-token counts.

The model is still Qwen3.8-Flash-Next, 125B, in NVFP4. Expert scores still
determine which experts compute each token. Hotness controls where their
weights live.

## What the comparison measures

The earlier post reported 346 tok/s prefill, 24 tok/s single-stream decode and
42 tok/s aggregate across eight streams. Those remain results for their
original workloads. This follow-up measures complete conversations under a
fixed single-request profile; it does not establish new values for that table.

For the new comparison I ran the original serving revision against the selected
runtime, then reversed the order. Each of the four starts had a fresh server,
one warmup conversation and two measured conversations. Server loading and
warmups were outside the measured totals. The host page cache was retained, so
reversing the order mattered.

| Measured work, per version | Original fork | Merged runtime |
|---|---:|---:|
| Three-turn conversations | 4 | 4 |
| Requests | 12 | 12 |
| Generated tokens | 5,374 | 5,374 |
| Total conversation wall time | 369.1 s | 252.4 s |
| Conversations passing the fixture checks | 4/4 | 4/4 |

The improvement held in both execution orders: 27.9% less time in the first
pair and 35.0% in the reverse pair. Complete answers and completion-token counts
also matched in the warmups. The [comparison harness](https://github.com/jomcgi-org/freetoken-fork/pull/55)
requires those checks before reporting a gain.

Both versions used the same model, cache geometry and request bodies. Better
prefix reuse meant the optimized version could skip more already-processed
input. That is useful work avoided while preserving the conversation, rather
than a shorter answer making the timing look better.

## Where the time went

There was no single replacement kernel responsible for the result. The selected
runtime combines several changes to how much work gets repeated and how much
data has to move.

| Change | Work removed |
|---|---|
| Quantize CPU prefill inputs once per token | Repeating the same input conversion for each selected expert |
| Stage selected DISK expert rows in bounded buffers | Reading and transferring a whole layer for a smaller set of needed experts |
| Reuse published HOT weights already in VRAM | Fetching another copy of weights the GPU already has |
| Carry frozen prefix state across short prefill chunks | Losing usable cached state at a chunk boundary |
| Reclaim redundant HOT file pages | Keeping avoidable disk-backed copies in a crowded host page cache |
| Gate invasive diagnostics | Synchronization and host readbacks needed only to observe the engine |

The staged prefill path still has a CPU fallback. A transfer only helps when
there is enough work to repay its cost. Likewise, reclaiming a file page leaves
the immutable checkpoint mapping valid: a later CPU read can fault the original
bytes back in.

These changes were measured together. An incremental improvement from an
earlier experiment is already included in the final total; the percentages
cannot be added.

### Measuring the measurement

Some telemetry had made its way into the normal execution path. Per-step CUDA
timing and diagnostic readbacks can introduce waits into the work being timed.
The selected runtime gates that work behind explicit diagnostic settings.

I used invasive probes to investigate individual mechanisms, then measured
wall time with those probes off. The original version still had some
unconditional diagnostic work, so removing it is part of the combined gain.
Synchronization that protects transfers and cache updates remains in place.

## Does it finish coding tasks sooner?

I also took two short tasks from the [LLM leaderboard](/llm-leaderboard) and ran
each twice per version, preserving their prompts, tools, budgets and graders.
These were multi-turn coding attempts, including tool execution and final
checks. The [task comparison](https://github.com/jomcgi-org/freetoken-fork/pull/60)
retained every attempt, including failures.

| Across four attempts per version | Original fork | Merged runtime |
|---|---:|---:|
| Total task wall time | 984.3 s | 795.6 s |
| Attempts passing the grader and permitted-file checks | 3/4 | 4/4 |

The selected version spent **19.2% less total time** and completed all four
attempts successfully. The original total includes a failed attempt that
finished relatively quickly. Agent trajectories and output lengths also
differed, so this is a task-completion result, not an isolated measure of engine
speed. It is separate from the matched-conversation result above.

This small sample does not establish broad quality equivalence. It does check
something a token-rate benchmark misses: whether the faster run actually
delivered the requested changes.

## What I kept out

Speculative decoding and a paired CPU kernel produced useful component results,
but did not establish a consistent improvement on the matched multi-turn
workload. Some coding runs looked much faster with speculation and also
generated substantially fewer tokens. That did not establish how much faster
the engine itself had become.

Those experiments remain separate. The merged configuration evaluates every
expert selected by the model and retains the qualified precision. There is
still room to investigate batching and GPU dense operations, but I wanted a
usable fork with the improvements already supported by the measurements.

## Running this version

The [merged revision](https://github.com/jomcgi-org/freetoken-fork/tree/32ad58f194bce8a85980202a5e9fd806f2848f17)
includes a [4090 launch profile](https://github.com/jomcgi-org/freetoken-fork/blob/32ad58f194bce8a85980202a5e9fd806f2848f17/docs/4090-performance.md).
After building the fork, including its updated native CPU extension:

```sh
bash scripts/serve-qwen-flash-4090.sh /path/to/flash-e2m1.ftw /path/to/layer-profile.json
```

This profile uses one running request, 14 CPU threads, a 6 GiB HOT budget and
65,536 reserved KV tokens with FP8 KV. In-memory prefix caching stays active;
disk prefix persistence and automatic KV growth are disabled. It is a different
capacity profile from the earlier 100k-context and eight-stream measurements.

The deployed runtime matches the qualified source, and real completions and a
follow-up exchange passed after cutover. Detailed request records and diagnostic
payloads remain private. The published figures here are the aggregate results
for these specific comparisons.
