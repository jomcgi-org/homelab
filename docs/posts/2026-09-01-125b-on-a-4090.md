## 1. FreeToken

[FreeToken](https://github.com/FlashML-org/FreeToken) is FlashML's engine for running mixture-of-experts models. It serves models larger than VRAM by keeping the experts in pinned RAM and caching the hot ones in VRAM.

This does not work for my node with 24GB VRAM + 64GB RAM, this post (& [fork](https://github.com/jomcgi-org/freetoken-fork)) is an experiment where I spill experts to disk to accommodate a larger than memory model.

These weights don't fit in VRAM or RAM and I can't convince myself to upgrade in this RAM economy so here we are spilling to disk.

The diagram and budgets below describe the original September 1 configuration. Later changes protect hot rows in GPU slots without a full pinned-host mirror and grow KV capacity on demand.

## 4. Follow one request

The useful question is not just whether the model fits. It is what the next token has to wait for.

A request has two phases. **Prefill** processes the prompt in chunks and builds the state needed to continue it. **Decode** then generates one token at a time, feeding each token back through the model. A reusable prefix can skip some prefill, but a new document has to do the work.

![Follow one request through the tiers](figures/request-path.svg)

| Key | Part |
|---|---|
| 1 | Make room: admit the request, find reusable prefix state, and allocate KV capacity. KV and expert slots share the GPU, so the KV pool starts small and grows at request boundaries; the pinned budget shares host RAM with the page cache that disk-backed experts need |
| 2 | Prepare the inputs: Qwen's 27 GB per-layer embedding (PLE) table is an additional lookup path, not a property of every MoE. Its n-gram ids follow from tokens we already know, so the rows are read once from NVMe into pinned staging and copied to the GPU before the forward pass |
| 3 | Run the layer and route: attention or GDN processes the current state, then the router selects 10 of this model's 512 experts per MoE layer. Unlike PLE ids, the choice depends on the forward computation. Prefill selects many distinct experts across a chunk; decode needs far fewer |
| 4 | Get the selected experts ready: a GPU-resident expert needs no transfer, a pinned-host expert is copied over PCIe into a slot, and a cold disk-tier expert is read through the page cache and computed on the CPU |
| 5 | Compute and join: GPU and CPU expert contributions combine before the next layer can start. The layer waits for the slower side even when the other processor is idle |
| 6 | Emit and repeat: after the final layer the output head and sampler choose a token, stream it, and feed it back to stage 2 until finished. Routing counters also retune the hot set for later work |
| A | GPU: dense layers, the expert slot cache with the hot set, and the KV cache |
| B | Pinned host memory: whole expert layers, 40 GB |
| C | Page cache |
| D | NVMe: expert banks and the lookup table |
| E | CPU MoE executor |

Startup sets the budgets that stage 1 works within. Prefill runs stages 2 to 5 once per chunk. Decode runs them once per token. Generation is the loop through stage 6, and what it leaves behind for the next turn. That gives us three different waits to explain: time to the first token, time between tokens, and how the whole answer holds up. A larger GPU cache, faster disk, or better CPU kernel helps only when it shortens the path the request actually takes.

## 5. Bottlenecks, in request order

### 5.1 Startup: budget the tiers before any request

My first mistake happened before inference: pinning 52 of the host's 64 GB left too little room for the page cache. The initial run recorded 96k major faults per decode step and 3.8 tok/s. Dropping the pinned budget to 40 GB tripled throughput. Pinning more weights had made accessing the remaining weights much slower.

The newer memory governor budgets pinning and paging together and respects cgroup limits. On the GPU, KV state competes with the expert cache too. The KV pool now starts small and grows at request boundaries. In the measured 100k-context configuration, this left about 14% more expert slots available at startup without lowering the context ceiling. It does not make a full 100k context free: those slots are surrendered as the KV pool grows.

### 5.2 Prefill: time to the first token

The upstream prefill path copied whole expert layers to the GPU. For a disk-backed layer, even a short prompt could bring in the entire bank. Running only the routed experts on the CPU took the original 441-token prompt from 17 minutes to 29 seconds. Overlapping pinned-layer transfers with computation subsequently lifted warm prefill from 54 to 116 tok/s.

The PLE table has its own path. The original post used direct GPU reads from host file mappings; that was a useful experiment, but two UVM kernel failures retired that backend on this box. For prefill the token IDs are already available, so the serving configuration now deduplicates the lookup rows for a chunk and reads them with `io_uring` into bounded pinned staging before the chunk's forward pass. That replaces demand faults inside GPU execution with explicit, batched I/O.

The newer path also uses the GPU hot set during prefill: hot routes run there, while cold routes use batched CPU matrix operations. Reusing an expert across many prompt tokens should become one batch of work, rather than repeated single-token calls. Explicit populate-reads bring selected expert pages into the page cache; releasing those pages after every layer was a loss because the next chunk often needed them again.

This improved the workload that matters for a new document. A measured 26,812-token novel prompt reached its first token in 77.4 seconds on September 3; similar prompt sizes had taken 7 to 14 minutes on September 1. This is a different workload from the 441-token warm benchmark, not a replacement number for that row.

### 5.3 Decode: one token step

Decode walks the same tiers with a much smaller expert set, so the fixed costs of each step show. The `io_uring` gather took 0.47 ms per decode step with zero PLE major faults in the September 3 measurement. Expert-bank faults are a separate path and still matter.

Disk-tier decode used `MADV_WILLNEED` to ask the kernel to prepare each selected expert's pages. Deduplicating selected experts reduced redundant requests, but even resident pages cost time to advise: the kernel still walks the range.

Timers attributed 331 of a 356 microsecond per-layer wake bucket to that callback. A recent-use policy now skips advice for experts used on the same layer within the preceding 256 decode steps. A fault guard restores conservative advice when residency assumptions stop holding, for example after a large prefill.

In that experiment, this removed about 8 ms from a 41 ms step.

On the 4090 host, the cold expert tail is cheaper to compute on the CPU than to ship across PCIe. The CPU returns a small activation vector rather than megabytes of weights. Protecting frequently used disk-tier experts in GPU slots cut distinct CPU experts per step from 58 to 18 in the original experiment.

But the CPU/GPU join is still on the request path. Profiling showed substantial CPU barrier spinning; replacing the spin or changing worker counts did not produce a reliable throughput gain once page-cache effects were accounted for. Time appearing in a profile is a clue, not proof that removing it speeds up the request.

### 5.4 Generation: the whole answer

Over a whole answer the per-step numbers compound with what came before. A warm single stream measured roughly 22 to 24 tok/s in the September 4 serving probes; those are workload measurements, not a guarantee for every prompt or context size. The harder case is what a long prompt does to the turns after it.

A hot set learned from one workload drifts when the workload changes. The original fix replaced a static routing profile with decayed counters and bounded background swaps. The newer failure was inside a single request: a long prefill flooded those counters with document routes, displacing experts needed by the conversation afterwards.

The serving policy now keeps separate prefill and decode histories and aims at the current phase. It also persists the hot plan across restarts and adapts during idle periods.

For the position-matched 76k-document experiment, shared histories delivered 12.5 tok/s on the following turns; split histories with phase-aware aim delivered 14.6 tok/s. Prompt processing took 664 and 652 seconds respectively. That is about 17% faster follow-up generation, with similar prefill time in this measurement.

An earlier configuration reached 19.2 tok/s but took 885 seconds to prefill. It over-weighted decode after a normalization interaction. Those faster decode figures should not be presented as the deployed configuration's result.

The measurement lesson belongs here too: ensure a prefill benchmark misses the prefix cache, and ensure the adapter actually ticks during both arms. Otherwise the experiment can completely bypass the mechanism being tested.

## 6. Ideas that didn't pan out

I thought these should have worked but measured them as losses. Each mechanism is still in the fork, off by default, with the reason next to the flag.

| Tried | Why it lost | Verdict |
|---|---|---|
| Let the GPU pull cold experts over PCIe instead of computing them on the CPU | About 990 expert fetches a step, 2.6 MB each, churn the slot cache faster than it can hold anything; single stream fell to 10 tok/s | Off below 48 GB of VRAM. Expected to be the cold-tail path for a 96 GB card |
| Split the cold tail between PCIe fetch and the CPU | On this host the CPU computes an expert faster than PCIe delivers it; 13.8 vs 19.5 tok/s | Off, same reason |
| Page in cold rows with a userspace pager instead of kernel hints | Faults dropped to 13 a step, but the pager is still page-granular and slightly slower than the hints; under-budgeted it evicted 1.6 million times | Kept for banks bigger than RAM, with a budget that covers the working set |
| Prefetch next step's experts ahead of the router | The next step is only 48% predictable, so the prefetch doubled the pages pulled in for half a hit | Off |
| Speculative decode (draft, then verify) | New tokens still route to additional experts, and rejection can require replay. Missing verify CUDA graphs added a second cost. September 4: 16.1 tok/s with eager verify, 19.5 with captured verify, versus 21.5 with MTP off, at 72% acceptance | Capturing verify recovered performance but still lost to ordinary decode on this box |


## 7. Scaling to a larger GPU and model

I also tested **GLM 5.3 Flash NVFP4** on a GCE `g4-standard-48` with one **96 GB RTX PRO 6000 Blackwell**, about **176 GB of reported host RAM**, and **four local NVMe SSDs in RAID 0**. Its converted checkpoint is 177 GiB. These are results from a larger machine, not GLM results on the 24 GB 4090.

| Measurement | Result | Conditions |
|---|---:|---|
| Single-stream throughput, September 4 | **12.12 tok/s** | Mean of three runs, F1: pin budget 112, hot budget 48 |
| Single stream with split histories and phase aim | 12.37 tok/s | Same day's F1b; the roughly 2% difference is too small to call a win |
| Single stream with the cold tail on CPU | 9.80 tok/s | Same day's F5a; slower than the PCIe path |
| Prefill, September 3 | 257 tok/s | Settled F1 run on 2k cold prompts; hot-set fill initially measured 28 and 49 tok/s |
| Four streams, September 3 | 19.3 tok/s aggregate | Total across four requests, not per user |
| Prompt/quality checks, September 3 | 8/8 passed | Fixed build, thinking off and on; a small functional check, not a general quality evaluation |

At 12.12 tok/s, a 300-token continuation is roughly 25 seconds of generation, calculated from that rate, plus prompt processing. That is slow, but enough for a patient conversation or a task I can leave running. Thinking tokens also consume generation time before a visible answer.

![Choose the path that finishes sooner](figures/two-machines.svg)

| Key | Part |
|---|---|
| 1 | Qwen on the RTX 4090: 64 GB of host RAM against 63.5 GB of experts, so most layers stay on disk. The cold tail is computed on the CPU and only a small activation comes back; fetching it over PCIe instead fell to 10 tok/s from 19.5 |
| 2 | GLM on the RTX PRO 6000: 176 GB of host RAM pins 29 of 42 MoE layers, and the hot set already covers 99.8% of the routes in the 13 disk layers. A miss streams whole experts over PCIe, about 3.1 GB a token; computing the tail on the CPU instead fell to 9.8 tok/s from 12.1 |
| A | GPU: expert slot cache with the hot set, and the KV cache |
| B | Pinned host memory |
| C | Page cache |
| D | NVMe |
| E | CPU MoE executor |

The 4090 optimizations did not all transfer. The GLM baseline's hot set already covered almost every observed route within its disk-tier layers. Its pinned layers still had to move weights over PCIe, so improving disk-tier hit rates barely moved throughput. The benchmark notes estimate roughly 3.1 GB of PCIe traffic per token; that is an explanatory estimate, not a direct byte-counter measurement.

Putting more of GLM on the CPU reduced faults but lowered throughput to 9.80 tok/s. Fewer faults are useful only if the replacement path is faster. The two machines choose opposite cold-expert paths for the same reason: on the 4090 nothing pins whole, so CPU compute beats PCIe; on the PRO 6000 most of the model pins, so PCIe beats the CPU. The best execution policy depends on the model, memory budgets, and processors together.

Two hardware conditions decided the result before any tuning. The tested 64 GB host-memory cap was unusable with this configuration. And the storage underneath the page cache still matters: the replication fell to 0.08 to 0.92 tok/s on a boot disk provisioned at 5,700 IOPS, then recovered to 12.1 tok/s with local NVMe. Sequential bandwidth alone did not predict this scattered-read workload. The usable result needs its hardware conditions beside it.

## 8. What does this actually mean?

A model larger than GPU memory can be served at usable speeds on hardware I already own. Qwen3.8-Flash-Next runs on a 24 GB card and 64 GB of RAM at about 21 tok/s for one stream and 37 across eight, and a new 27k-token document reaches its first token in 77 seconds.

The gains came from following the request rather than the model: budget the tiers at startup so the page cache can work, stage what is already known before the forward, route before fetching, compute the cold tail where it is cheapest, and keep the hot set aimed at the phase that is running. Every fix that held shortened one wait on that path. The ones that did not, in section 6, added work beside it.

The same tiering on a larger GPU does not carry the same tuning. Once most of the model pins, PCIe bandwidth sets the limit and the CPU tail loses. On a new machine, find which wait dominates before pulling any lever.

I still would not buy a machine on the strength of token throughput alone. The [fork quickstart](https://github.com/jomcgi-org/freetoken-fork/blob/feat/moe-disk-tier/QUICKSTART.md) describes how to run it. The [benchmark record](https://github.com/jomcgi-org/freetoken-fork/blob/0b7ad70f925c1a998e09d357243f8ea2e6f899af/bench/RESULTS.md) separates the experiments and their conditions.
