I'm serving Qwen3.8-Flash-Next, a 125B mixture-of-experts model, on a 24 GB
RTX 4090 with 64 GB of RAM. With NVFP4 expert weights and a quantized lookup
table, the model takes about 100 GiB.

[FreeToken](https://github.com/FlashML-org/FreeToken) already runs models larger
than VRAM by keeping expert weights in pinned RAM and caching them on the GPU.
This didn't fit on my node. I can't convince myself to upgrade in this RAM
economy, so here we are spilling experts to disk. This post follows a request
through my [fork](https://github.com/jomcgi-org/freetoken-fork) and the problems
I ran into getting it reasonably responsive.

## How MoE works

Each token triggers a small number of experts. These are feed-forward
networks within a layer of the model. A learned router picks which ones
process the token's current vector, then their outputs are combined using
the router's weights. This is the
[sparse MoE mechanism](https://arxiv.org/abs/1701.06538).

![A router selects experts and combines their outputs](figures/moe-selection.svg)

| Key | Part |
|---|---|
| 1 | The router scores experts using the token's current vector. |
| 2 | The selected experts each process that vector. Two of five are shown for illustration. |
| 3 | A weighted sum combines their outputs before processing continues. |

Qwen selects ten of 512 routed experts in each of its 48 expert layers,
alongside a shared expert. About 6B of its 125B parameters are active per
token. The token still passes through all the layers and uses shared
operations such as attention.

The router makes a fresh decision at each layer, using the result of the work
before it. The experts selected for the next layer, or the next generated
token, can be different. All their weights must remain available even though
only a fraction are used at once.

I can keep the frequently used experts in VRAM and fetch the others as
required. The location of their weights decides how long it takes to access
them and the type of compute they land on. Every expert the router selects
still has to run.

## Where the weights live

![GPU memory, pinned RAM, the page cache and disk](figures/memory-tiers.svg)

| Key | Part |
|---|---|
| 1 | The 24 GB GPU holds shared weights, cached conversation state and expert slots. Frequently used experts occupy a protected hot set. |
| 2 | PCIe carries weights and token vectors between host memory and the GPU. |
| 3 | Pinned RAM holds expert banks and small transfer buffers. The operating system cannot reclaim this memory for its page cache. |
| 4 | The page cache holds recently read file pages in ordinary RAM. It shares the host's 64 GB with pinned allocations, the server and the operating system. |
| 5 | The NVMe stores all 63.5 GiB of expert banks and a separate 27 GiB lookup table. Cached copies above it use additional space. |
| 6 | The CPU can compute selected experts using their file-backed weights. Pages missing from RAM must first be read from disk. |

The experts on disk are read-only mappings of the weight files. Linux keeps
recently read pages in RAM, so accessing a disk expert can hit the page cache
without touching the NVMe. If those pages have been evicted, I have to wait
for storage again.

Mapping the weight file with `mmap` makes both cases look like memory access
to the program. It does not make them equally fast. A major page fault means
the access needs I/O before it can continue.

I initially pinned too much RAM. That left almost nothing for the page cache
to manage access to the disk experts. Decode kept waiting for reads.

This was terrible. Reducing the pinned budget made it faster.

I budget pinning and paging together now. Pinned memory can't be reclaimed
by the operating system, so every extra bank I pin takes room away from the
page cache.

On the GPU, conversation state competes with expert weights. Attention's
key/value cache, or KV cache, stores prior tokens' keys and values so they can
be reused. Reserving more context up front leaves fewer expert slots. I added
support for growing that reservation between requests. Long conversations
take those slots back.

The measurements below use a fixed 65,536-token reservation. A 100k-context
run or an eight-stream run leaves a different amount of room for experts.

## A request arrives

Suppose I send a document and ask for a summary. The server tokenizes the
prompt and checks whether it has already processed an identical prefix.
If it has, it can reuse that state and skip the corresponding prompt work.

The remaining input goes through **prefill**: processing known prompt tokens,
in chunks, to produce the state needed to start answering. **Decode** then
generates the answer one token at a time. Each new token becomes input to the
next step.

One trap here: a prefill benchmark has to miss the prefix cache. Otherwise I
can measure how quickly I skipped the work and think I've improved it.

## Reading the prompt

During prefill, many tokens can select the same expert. Fetching that expert
once lets the engine process all those token vectors together. A chunk can
also select a large fraction of a layer's experts, even though each individual
token uses only a few.

FreeToken streams whole expert layers to the GPU. That works well when the
bank is in pinned RAM: the next transfer can overlap GPU computation. For my
disk layers it meant paging in the entire bank, including hundreds of
experts a short prompt never selected. Those reads also displaced useful
pages from the cache.

My first patch routed prefill for disk layers through the CPU executor,
which only touches experts that the router selected. The disk path waits
for each layer's routing, deduplicates the selected experts and reads their
rows from the weight banks. Later layers haven't routed yet, so their expert
IDs aren't available.

The CPU groups token vectors by expert and processes each group together.
Each token's input is quantized once and reused across its selected experts.
I populate the pages with explicit reads before the multiplication, so the
CPU doesn't discover every missing page while trying to compute. The next
chunk often needs many of the same experts.

Larger chunks have enough work per expert to justify copying the selected
weights to the GPU. I stage those weights through small pinned buffers into
GPU scratch space. Experts already in the GPU hot set use their resident
weights. Smaller chunks stay on the CPU. A staging buffer has to finish its
transfer before I can reuse it.

### The other 27 GiB

Qwen also has a per-layer embedding (PLE) table indexed by
n-grams, combinations of recent token IDs. It is separate from the experts.
I use a four-bit E2M1 representation of this table. Its rows depend on the
input tokens, so I know a prefill chunk's lookup IDs before the model runs.
Expert IDs become known only after each layer routes.

Having the GPU read the host file mappings directly was faster in my early
tests. Two UVM kernel failures pushed me to `io_uring`: dedupe the known
table rows, read them into pinned host memory, then copy them to a compact
GPU buffer. Decode uses the same path for its smaller set of known IDs.

The reads finish before the GPU starts using the rows. This also keeps file
I/O outside CUDA graph replay, the pre-recorded GPU execution sequence used
for decode.

The table and the experts compete for the same host memory. A large pinned
table cache leaves less room for expert pages, even if the table's own reads
look efficient. Using small staging buffers freed room for expert pages.

## Writing the answer

Now the model generates the answer one token at a time. For a single request,
an expert may have just one token to process before the model moves to the
next layer. There is much less work to justify fetching its weights.

![One decode step routes experts across the memory tiers](figures/decode-step.svg)

| Key | Part |
|---|---|
| 1 | Route the token's current vector to the selected experts in this layer. |
| 2 | Look up where each selected expert is available. Residency changes the execution path, while the router's selection stays intact. |
| 3 | Reuse GPU weights, fetch pinned weights over PCIe, or run a cold expert on the CPU using the page cache. A cache miss adds an NVMe read. |
| 4 | Combine the GPU and CPU contributions using the routing weights, then continue through the model. Record expert usage for cache adaptation. |
| A | GPU expert slots, including the protected hot set, and conversation state. |
| B | Pinned host expert banks. A GPU cache miss here needs a transfer but no disk read. |
| C | The host page cache. A hit lets a file-backed expert run on the CPU without storage I/O. |
| D | NVMe expert banks and the PLE table. PLE rows are staged before the forward pass. |
| E | The CPU expert executor, which returns its output vectors to the GPU. |

A GPU-resident expert needs no host weight transfer. An expert in pinned RAM
can be copied into a GPU slot, but PCIe is slower than reading local VRAM.
If the slot cache already has it, that copy can be skipped too.

I thought fetching cold experts to the GPU should have worked. It measured
as a loss on this box. The CPU can read the weights through the page cache
and return a small activation vector instead of megabytes of weights.
Prefill can reuse the transferred weights across a batch of tokens. Decode
often only gets one.

A page-cache miss still stalls the cold path. The router provides a short
window to request the selected pages before the CPU uses them, but a memory
mapping and a prefetch hint do not guarantee residency. The layer must wait
for every selected expert's contribution, including the slow ones.

I also tried prefetching before routing. That meant guessing which experts
would be selected, and the extra reads lost on this box. With little spare
RAM, fetching the wrong weights can evict the ones the request actually
needs. I wait for the router so I know what to read.

## Between steps and turns

Our router didn't spread load evenly across experts. Depending on the task,
a small number served most of the routes while the rest were used
occasionally. Keeping those hot experts nearby helped, but I hardcoded a
captured routing profile. As soon as traffic changed the hit rate fell,
wiping out the gain.

I replaced the static profile with a per-expert counter that decays over
time. Prefill and decode keep separate histories. Otherwise a long document
can dominate the counters just before a short conversation needs a
different set of experts.

Replacement weights are copied in small background batches. The old expert
keeps serving while the replacement is staged, then the slot mapping changes
between steps once the copy is complete. No route ever sees a half-installed
row. Once an expert is installed in VRAM, its redundant file pages can be
released from the host cache. The weight file stays on disk.

On the next chat turn, I can ask a follow-up about the document. Prefix reuse
can avoid processing it again.
The reusable state includes the model's recurrent state as well as attention
KV. I keep that prefix state across short prefill chunks so a chunk boundary
doesn't discard work the following turn could reuse.

## What this machine can serve

With [these changes together](https://github.com/jomcgi-org/freetoken-fork/tree/32ad58f194bce8a85980202a5e9fd806f2848f17),
I measured **about 21 generated tokens per second** across four conversations
on the 4090. That includes prompt processing and request overhead.

| Measured workload | Result |
|---|---:|
| Three-turn conversations | 4 (12 requests) |
| Generated tokens | 5,374 |
| Total conversation wall time | 252.4 s |
| Conversations passing the fixture checks | 4/4 |

I ran one request at a time, with 14 CPU threads, a 6 GiB GPU hot set and
65,536 reserved KV tokens using FP8 KV. Each server start had a warmup
conversation before measurement. Loading and warmup time are excluded, and
I kept the host page cache. These are warm conversation results, with prefix
reuse available. A new long document still has to pay for prefill.

I turned off per-step GPU timers and diagnostic host readbacks for these
runs. Those probes can force synchronization and change the time being
measured. The waits needed to protect transfers and cache updates remain.

### With enough RAM or VRAM

I wanted to put this beside the same model running with enough RAM, or
enough VRAM for the experts. These are published single-stream results with
NVFP4 expert weights:

| Setup | Where the experts live | Reported rate |
|---|---|---:|
| This fork, RTX 4090 24 GB + 64 GB RAM | GPU hot set, pinned RAM and disk | 21.3 output tok/s across complete conversations |
| [Upstream FreeToken, RTX 4090 24 GB](https://github.com/FlashML-org/FreeToken/pull/257), 128 GB RAM recommended | GPU cache backed by pinned RAM | 36 decode tok/s |
| [SGLang, RTX PRO 6000 96 GB](https://github.com/lEWFkRAD/qwen38-rtx-pro-6000/blob/59f59a86245bc63ff7f74d775b890a0bd9888734/flash-next-w4-ple/docs/CACHED-NEXTN-REPLAYSSM-PRODUCTION-ADDENDUM-2026-09-01.md) + 64 GB RAM | Experts in VRAM, PLE table in host RAM | 97.9 decode tok/s; 96.5 end-to-end tok/s |

The RAM-backed 4090 result is the closest hardware reference. It uses AIME25,
50,000 reserved KV tokens and about 111 GiB of pinned host memory, including
a 48 GiB FP8 PLE table. The SGLang row is its non-speculative control: six
measured 512-output-token runs after warmup, with device prefix caching and
a signed-INT4 PLE table. Its experts fit on a much larger, newer GPU; the
whole model is still not entirely in VRAM.

My conversation rate includes prefill. The prompts, cache budgets and PLE
representations differ too. I can't use these numbers to say how much disk
costs in percentage terms. That needs a matched decode benchmark.

## Running it

My node has an RTX 4090, a Ryzen 7800X3D, 64 GB DDR5-6000 and a 1.9 TB
NVMe. The checkpoint uses about 63.5 GiB for expert banks, 9.2 GiB for shared
weights and 27 GiB for the PLE table. Runtime caches need space as well.

If you want to run it yourself, the
[build and launch instructions for the measured revision](https://github.com/jomcgi-org/freetoken-fork/blob/32ad58f194bce8a85980202a5e9fd806f2848f17/docs/4090-performance.md)
include rebuilding the native CPU extension. That launch profile keeps
in-memory prefix caching on and disk prefix persistence and automatic KV
growth off. A [later launch-profile change](https://github.com/jomcgi-org/freetoken-fork/pull/67)
enabled disk prefix persistence by default. Persisting conversation state is
a separate use of disk from storing expert weights, and was outside the
conversation measurements above.

The [benchmark notes](https://github.com/jomcgi-org/freetoken-fork/blob/32ad58f194bce8a85980202a5e9fd806f2848f17/bench/RESULTS.md)
and [conversation harness](https://github.com/jomcgi-org/freetoken-fork/pull/55)
keep the experiment details and measurement methods together.

## What does this actually mean?

Should you go out and buy a 4090 to run models this way? Probably not.
Unless you've already got the hardware, I'd price out the API usage before
buying a node for this.

I wanted to see how far I could get with the machine I had. It now serves
a model larger than its combined RAM and VRAM at a rate I can use.

I'm in the process of moving from Canada to the UK at the moment, so this
will shape the type of node that I buy when I get over there!
