## 1. FreeToken

[FreeToken](https://github.com/FlashML-org/FreeToken) is FlashML's engine for running mixture-of-experts models. It serves models larger than VRAM by keeping the experts in pinned RAM and caching the hot ones in VRAM.

This does not work for my node with 24GB VRAM + 64GB RAM, this post (& [fork](https://github.com/jomcgi-org/freetoken-fork)) is an experiment where I spill experts to disk to accommodate a larger than memory model.

| Context window | 100k |

The weights don't fit in VRAM or RAM and I can't convince myself to upgrade in this RAM economy so here we are spilling to disk.

## 4. How does MoE inference work?

We generate a token by running every layer once. In a mixture-of-experts layer the router looks at your input and picks a handful of the 512 experts to run.

That means that most of the 63.5 GB of expert weights are idle during token generation, the work to optimize this in a resource constrained environment is then less about the computation and more about getting the chosen experts to the most efficient place for that computation to happen. 

Decoding is one token at a time with a few experts per layer and it is bottlenecked by the slowest tier that it has to reach into. Prefill pushes the whole prompt through at the same time so it touches many experts per layer and looks more like compute but on this box it still has to find the experts first.

[Qwen3.8-Flash-Next](https://qwen.ai/blog?id=qwen3.8-flash-next) is a preview of their Qwen 4 architecture including an n-gram lookup table which is 27 GB of learned rows keyed by the last couple of tokens so that it can be retrieved during inference instead of computed.

The bandwidth tiers with time taken to move one 2.6 MB expert are:
* VRAM (1TB/s ~3us)
* RAM over PCIe (25GB/s ~100us)
* Page cache (hit: RAM speed ~40us; miss: a 15us fault per 4KB page, ~10ms)
* DISK (7GB/s ~370us when read in bulk)

## 5. Bottlenecks

The many problems I ran into trying to get this working with a reasonably responsive throughput.

### 5.1 Pinning too much starved the page cache

FreeToken pins expert banks into memory, my initial budget was 52/64GB which left nothing for page cache to manage access to 57GB of disk-resident data.

This was terrible, the result was 96k major faults per decode step & 3.8 tok/s throughput.

Dropping the budget to 40GB tripled throughput by letting the page cache manage the disk reads. 

### 5.2 Random reads from disk (experts vs n-gram)

This is fine for experts because on disk they are a read-only mmap of the weight file, routing happens before the expert computes so we know what we need to load before they get used. With some batch deduplication I got <10 major faults per step for managing them.

The n-gram lookup is different. It's touched on every token at random rows from inside a CUDA graph. Having the GPU read the host file mappings directly was faster than trying to manage this in the caching tiers. Switching to that almost doubled four-stream throughput from 14 to 26.5 and freed the pinned cache that the table had been using leaving room to fit more experts onto higher bandwidth tiers.

### 5.3 Prefill was copying whole layers

The upstream implementation streams whole expert layers to the GPU, for a disk resident layer that meant paging in the entire bank regardless of prompt length.

My patch routed prefill for disk layers through the CPU executor which only touches experts that the router selected.

This reduced the time to process 441 tokens from 17m to 29s.

With some layers pinned and some on disk the pinned layers could overlap their PCIe transfer with compute while the disk layers prefilled on the CPU and chained the next pinned layer's prefetch. This took warm prefill from 54 to 116 tok/s.

![A prefill chunk: what is known before the forward and what is read once](figures/prefill-chunk.svg)

| Key | Part |
|---|---|
| 1 | Before the forward: the chunk's n-gram ids are computed from its input tokens and deduped. Nothing about them depends on the forward |
| 2 | One read each: the deduped table rows arrive in one coalesced read into a pinned GPU bank; after each layer's routing, its expert rows are populated into the page cache with real reads instead of advisory hints |
| 3 | Forward: the lookup resolves against the pinned bank by compact local id while the experts compute. Major faults per chunk fell from about 3.6 million to a few thousand |
| A | GPU, with the pinned staging bank |
| C | Page cache |
| D | NVMe: lookup table and expert banks |
| E | CPU MoE executor |

### 5.4 The CPU tier became a ceiling for perf

Residency was decided per layer, either pinned or on disk. But our router didn't spread load evenly across experts. Depending on the task a small number of experts may serve most of the routes while the rest are used occasionally.

Pinning the hot rows (about 6GB covering 72% of routes) and sending them through the GPU's expert slot cache while keeping the cold tail on CPU decode took single-stream from 19.5 to 23.1 and eight streams from 34 to 42.2 at peak, which settles to the 21 and 37 in section 3 on mixed traffic.

Distinct experts hitting the CPU per step fell from 58 to 18.

![One decode step through one expert layer at the final config](figures/decode-step.svg)

| Key | Part |
|---|---|
| 1 | Route: the router picks this token's experts from 512 in the layer. The n-gram ids are already known from the last few tokens |
| 2 | Sort by residency: each chosen expert is hot (resident on the GPU), pinned (in host memory), or cold (on the NVMe, possibly in the page cache). About 58 distinct experts a step before the hot set, 18 on the CPU after |
| 3 | Move: pinned experts stream over PCIe into a GPU slot; cold experts get one deduped willneed and are computed by the CPU out of the page cache; the GPU reads the n-gram rows straight through the file mapping |
| 4 | Compute and tally: the GPU and CPU partial outputs sum, and every routed expert bumps a decayed counter |
| A | RTX 4090: expert slot cache with the hot set resident, KV cache |
| B | Pinned host memory, 40 GB of expert banks |
| C | Page cache |
| D | NVMe: expert banks 63.5 GB, lookup table 27 GB |
| E | CPU MoE executor |

### 5.5 Is it hot or not? drifting expectations

5.4 was a step in the right direction but I hardcoded a captured routing profile, as soon as traffic changed the hit rate fell significantly wiping out the gain.

I got this back by replacing the static profile with a decayed per-expert counter and bounded background swaps (retire, copy, flip), this recovered the perf lost on generic workloads and improved cold start as the hot set assembled itself.

![How one hot-set slot changes hands without a stall](figures/hot-set-swap.svg)

| Key | Part |
|---|---|
| 1 | Tick: every 1,000 steps the decayed counters are re-ranked under the same 6 GB budget. One expert crosses into the hot set, one drops out |
| 2 | Stage: a background thread copies the newly hot rows from the NVMe into staging, at most 0.5 GB a tick. The retiring expert keeps serving from where it was |
| 3 | Flip: at a step boundary the mapping points at the staged row and the retired slot is free. No route ever sees a half-installed row |
| A | GPU slot cache, one hot slot of the 6 GB |
| D | NVMe expert banks |

## 6. Ideas that didn't pan out

I thought these should have worked but measured them as losses. Each mechanism is still in the fork, off by default, with the reason next to the flag.

| Tried | Why it lost | Verdict |
|---|---|---|
| Let the GPU pull cold experts over PCIe instead of computing them on the CPU | About 990 expert fetches a step, 2.6 MB each, churn the slot cache faster than it can hold anything; single stream fell to 10 tok/s | Off below 48 GB of VRAM. Expected to be the cold-tail path for a 96 GB card |
| Split the cold tail between PCIe fetch and the CPU | On this host the CPU computes an expert faster than PCIe delivers it; 13.8 vs 19.5 tok/s | Off, same reason |
| Page in cold rows with a userspace pager instead of kernel hints | Faults dropped to 13 a step, but the pager is still page-granular and slightly slower than the hints; under-budgeted it evicted 1.6 million times | Kept for banks bigger than RAM, with a budget that covers the working set |
| Prefetch next step's experts ahead of the router | The next step is only 48% predictable, so the prefetch doubled the pages pulled in for half a hit | Off |
| Speculative decode (draft several tokens, verify in one pass) | Speculation pays when a marginal token is cheap. With part of every step on the CPU tier a drafted token costs full price, even at 72% acceptance; 12.6 vs 18.0 tok/s | Closed on this box, untested with everything pinned |


## 7. What does this actually mean?

Should you go out and buy a 4090 or an RTX 6000 to run models this way?
Probably not. Inference over API is so cheap that unless you've already got the hardware it's likely cheaper to just pay for API pricing.

My takeaway is that frontier intelligence at home is closer than ever and that the serving methods / model distributions will only become more efficient.
I'm in the process of moving from Canada to the UK at the moment so this will shape the type of node that I buy when I get over there!
