I'm serving Qwen3.8-Flash-Next, a 125B mixture-of-experts model, on a 24 GB
RTX 4090 with 64 GB of RAM. With NVFP4 expert weights and a quantized lookup table, the model takes
about 100 GiB. Some of it has to live on disk.

[FreeToken](https://github.com/FlashML-org/FreeToken) already runs models larger
than VRAM by keeping expert weights in pinned RAM and caching them on the GPU.
With this model and memory budget, upstream FreeToken could not start.
I [forked it](https://github.com/jomcgi-org/freetoken-fork) to add a disk tier. I can't convince myself to upgrade in this
RAM economy, so here we are.

## How MoE works

A language model processes tokens, the pieces of text produced by its
tokenizer, through a sequence of layers. Each layer transforms a vector
representing the token. In a dense feed-forward layer, every token uses the
same weights. A mixture-of-experts layer has a pool of feed-forward networks
and a learned router that selects a few of them for each token. These networks
are the experts. Their outputs are combined using the router's weights.
This is the [sparse MoE mechanism](https://arxiv.org/abs/1701.06538).

![A router selects experts and combines their outputs](figures/moe-selection.svg)

| Key | Part |
|---|---|
| 1 | The router scores experts using the token's current vector. |
| 2 | The selected experts each process that vector. Two of five are shown for illustration. |
| 3 | A weighted sum combines their outputs before processing continues. |

Qwen selects ten of 512 routed experts in each of its 48 expert layers,
alongside a shared expert. About 6B of its 125B parameters are active per
token. The token still passes through all the layers and uses shared
operations such as attention; MoE makes the routed expert computation sparse.

The router makes a fresh decision at each layer, using the result of the work
before it. The experts selected for the next layer, or the next generated
token, can be different. All their weights must remain available even though
only a fraction are used at once.

That leaves an opening for a smaller GPU: keep frequently used experts nearby
and fetch the others when needed. The router still selects every expert the
model asks for. The cache decides where to execute them.

## Where the weights live

![GPU memory, pinned RAM, the page cache and disk](figures/memory-tiers.svg)

| Key | Part |
|---|---|
| 1 | The 24 GB GPU holds shared weights, cached conversation state and expert slots. Frequently used experts occupy a protected hot set. |
| 2 | PCIe carries weights and token vectors between host memory and the GPU. |
| 3 | Pinned RAM holds expert banks and small transfer buffers. The operating system cannot reclaim this memory for its page cache. |
| 4 | The page cache holds recently read file pages in ordinary RAM. It shares the host's 64 GB with pinned allocations, the server and the operating system. |
| 5 | The NVMe stores all 63.5 GiB of expert banks and a separate 27 GiB lookup table. Cached copies above it use additional space. |
| 6 | The CPU can compute selected experts using their file-backed weights. Pages missing from RAM must first be read from disk. |

An expert being "on disk" describes its backing store. Its bytes may already
be in RAM because Linux kept them in the page cache. A repeated read can then
run at memory speed. If those pages have been evicted, the same access waits
for storage.

Mapping the weight file with `mmap` makes both cases look like memory access
to the program. It does not make them equally fast. A major page fault means
the access needs I/O before it can continue.

There are two budgets to get right before accepting a request. On the host,
pinning more expert banks leaves less room to cache disk reads. The fork
budgets pinned allocations alongside the page cache. Pinning everything
that fits would leave the remaining experts repeatedly waiting for storage.

On the GPU, conversation state competes with expert weights. Attention's
key/value cache, or KV cache, stores prior tokens' keys and values so they can
be reused. Reserving more context up front leaves fewer expert slots. The
fork supports growing the reservation between requests. The measured
profile below uses a fixed 65,536-token reservation. A 100k-context run and
an eight-stream run have different memory budgets.

## A request arrives

Suppose I send a document and ask for a summary. The server tokenizes the
prompt and checks whether it has already processed an identical prefix.
Any reusable prefix state saves a corresponding portion of the prompt work.

The remaining input goes through **prefill**: processing known prompt tokens,
in chunks, to produce the state needed to start answering. **Decode** then
generates the answer one token at a time. Each new token becomes input to the
next step.

Both phases run the same model. They give the storage system very different
amounts of work to batch.

## Reading the prompt

During prefill, many tokens can select the same expert. Fetching that expert
once lets the engine process all those token vectors together. A chunk can
also select a large fraction of a layer's experts, even though each individual
token uses only a few.

FreeToken's whole-layer transfer works well when the bank is in pinned RAM:
the next transfer can overlap GPU computation. Applying that policy to a
disk-backed layer can read hundreds of experts a short prompt never selected.
Those bytes also displace useful pages from the host cache.

The disk path waits for the layer's router, deduplicates its selected experts
and reads the required rows. Here a "row" is one expert's slice of a weight
bank. The engine already has the token vectors for this layer; it cannot know
later layers' selections yet.

There are two ways to do the computation. The CPU path groups token vectors
by expert and runs a matrix multiplication for each group. It prepares each
token's quantized input once, reusing it across the selected experts. Pages
are populated with explicit reads so the CPU does not discover every missing
page while doing the multiplication. Keeping those pages available helps the
next chunk, which often selects many of the same experts.

For sufficiently large chunks, the staged path copies selected disk-backed
weights through bounded pinned buffers to GPU scratch space. The transfer
buys enough GPU work to be useful. Experts already in the GPU hot set supply
their weights from VRAM, without another host fetch. Smaller chunks retain
the CPU path. The buffers can be reused only after their previous transfers
finish.

### The other 27 GiB

This particular model also has a per-layer embedding (PLE) table indexed by
n-grams, combinations of recent token IDs. It is separate from the experts.
I use a four-bit E2M1 representation of this table. Its rows depend on the
input tokens, so a prefill chunk's lookup IDs are known
before the model runs. Expert IDs become known only after each layer routes.

That earlier knowledge lets the engine deduplicate and gather the chunk's
table rows ahead of time. `io_uring` submits the reads into pinned host
staging memory, then the rows are copied to a compact GPU buffer for the
forward pass. Decode uses the same idea for its smaller set of known IDs.

Direct GPU access to the host file mapping initially looked faster, but it
caused two kernel failures on this machine. Explicit staging also keeps file
I/O outside CUDA graph replay, the pre-recorded GPU execution sequence used
for decode. The GPU consumes rows that have already arrived.

The table and the experts compete for the same host memory. A large pinned
table cache leaves less room for expert pages, even if the table's own reads
look efficient. Small staging buffers make that memory available again.

## Writing the answer

Decode has much less work to reuse per fetched expert. In the single-request
case, an expert may be needed for just one token before the model moves to
the next layer. The GPU's arithmetic speed helps only after its inputs arrive.

![One decode step routes experts across the memory tiers](figures/decode-step.svg)

| Key | Part |
|---|---|
| 1 | Route the token's current vector to the selected experts in this layer. |
| 2 | Look up where each selected expert is available. Residency changes the execution path, while the router's selection stays intact. |
| 3 | Reuse GPU weights, fetch pinned weights over PCIe, or run a cold expert on the CPU using the page cache. A cache miss adds an NVMe read. |
| 4 | Combine the GPU and CPU contributions using the routing weights, then continue through the model. Record expert usage for cache adaptation. |
| A | GPU expert slots, including the protected hot set, and conversation state. |
| B | Pinned host expert banks. A GPU cache miss here needs a transfer but no disk read. |
| C | The host page cache. A hit lets a file-backed expert run on the CPU without storage I/O. |
| D | NVMe expert banks and the PLE table. PLE rows are staged before the forward pass. |
| E | The CPU expert executor, which returns its output vectors to the GPU. |

A GPU-resident expert needs no host weight transfer. An expert in pinned RAM
can be copied into a GPU slot, but PCIe is slower than reading local VRAM.
If the slot cache already has it, that copy can be skipped too.

For a cold expert, the CPU can read the weights through the page cache and
send back a small output vector. Moving that vector costs much less than
moving megabytes of weights. On this 4090 setup, that path beat fetching the
cold expert to the GPU for single-token work. Prefill can repay the transfer
with a batch of token vectors; decode often cannot.

A page-cache miss still stalls the cold path. The router provides a short
window to request the selected pages before the CPU uses them, but a memory
mapping and a prefetch hint do not guarantee residency. The layer must wait
for every selected expert's contribution, including the slow ones.

Prefetching before routing means guessing. With little spare RAM, fetching
the wrong weights can evict the ones the request actually needs. Waiting
for the router trades a longer lead time for a known set of reads.

## Between steps and turns

The hot set follows measured expert use. Counters decay so old traffic loses
influence, and prefill and decode keep separate histories. A long document
can otherwise dominate the counters just before a short conversation needs
a different set of experts.

Moving an expert into VRAM also takes work. The adapter stages replacement
weights in bounded batches and publishes ownership at a safe boundary, once
the copy is complete. Computation must never read a slot while its weights
are being replaced. Redundant file-backed copies of installed hot experts
can be released from the host cache; the checkpoint remains available if
those pages are needed again.

On the next chat turn, prefix reuse can avoid processing the document again.
The reusable state includes the model's recurrent state as well as attention
KV. The fork carries frozen prefix state across short prefill chunks so a
chunk boundary does not discard work the following turn could reuse.

## What this machine can serve

On the [integrated runtime](https://github.com/jomcgi-org/freetoken-fork/tree/32ad58f194bce8a85980202a5e9fd806f2848f17),
the 4090 averaged **about 21 generated tokens per second** across the measured
conversations. That includes prompt processing and request overhead.

| Measured workload | Result |
|---|---:|
| Three-turn conversations | 4 (12 requests) |
| Generated tokens | 5,374 |
| Total conversation wall time | 252.4 s |
| Conversations passing the fixture checks | 4/4 |

This profile runs one request at a time, with 14 CPU threads, a 6 GiB GPU hot
set and 65,536 reserved KV tokens using FP8 KV. Each server start had a warmup
conversation before measurement; loading and warmup time are excluded, and
the host page cache was retained. These are warm conversation results, with
prefix reuse available. A new long document still has to pay for prefill.

Per-step GPU timers and diagnostic host readbacks were off. Those probes can
force synchronization and change the time being measured. Synchronization
needed to protect transfers and cache updates remains.

### With enough RAM or VRAM

There are published single-stream results for the same model with NVFP4
expert weights and more memory. They give two useful reference points:

| Setup | Where the experts live | Reported rate |
|---|---|---:|
| This fork, RTX 4090 24 GB + 64 GB RAM | GPU hot set, pinned RAM and disk | 21.3 output tok/s across complete conversations |
| [Upstream FreeToken, RTX 4090 24 GB](https://github.com/FlashML-org/FreeToken/pull/257), 128 GB RAM recommended | GPU cache backed by pinned RAM | 36 decode tok/s |
| [SGLang, RTX PRO 6000 96 GB](https://github.com/lEWFkRAD/qwen38-rtx-pro-6000/blob/59f59a86245bc63ff7f74d775b890a0bd9888734/flash-next-w4-ple/docs/CACHED-NEXTN-REPLAYSSM-PRODUCTION-ADDENDUM-2026-09-01.md) | Experts in VRAM, PLE table in host RAM | 97.9 decode tok/s; 96.5 end-to-end tok/s |

The RAM-backed 4090 result is the closest hardware reference. It uses AIME25,
50,000 reserved KV tokens and about 111 GiB of pinned host memory, including
a 48 GiB FP8 PLE table. The SGLang row is its non-speculative control: six
measured 512-output-token runs after warmup, with device prefix caching and
a signed-INT4 PLE table. Its experts fit on a much larger, newer GPU; the
whole model is still not entirely in VRAM.

Our conversation rate includes prefill. The prompts, cache budgets and PLE
representations also differ across these runs. These figures put the finished
server in context; a matched decode benchmark would be needed to put a
percentage on the cost of disk tiering.

## Running it

The hardware is an RTX 4090, a Ryzen 7800X3D, 64 GB DDR5-6000 and a 1.9 TB
NVMe. The checkpoint uses about 63.5 GiB for expert banks, 9.2 GiB for shared
weights and 27 GiB for the PLE table. Runtime caches need space as well.

The [build and launch instructions for the measured revision](https://github.com/jomcgi-org/freetoken-fork/blob/32ad58f194bce8a85980202a5e9fd806f2848f17/docs/4090-performance.md)
include rebuilding the native CPU extension. Its launch profile keeps
in-memory prefix caching on and disk prefix persistence and automatic KV
growth off. A [later launch-profile change](https://github.com/jomcgi-org/freetoken-fork/pull/67)
enabled disk prefix persistence by default. Persisting conversation state is
a separate use of disk from storing expert weights, and was outside the
conversation measurements above.

The [benchmark notes](https://github.com/jomcgi-org/freetoken-fork/blob/32ad58f194bce8a85980202a5e9fd806f2848f17/bench/RESULTS.md)
and [conversation harness](https://github.com/jomcgi-org/freetoken-fork/pull/55)
keep the experiment details and measurement methods together.

Disk gives this machine enough capacity to hold the model. Making a request
responsive depends on how often its selected weights are already nearby,
how much computation reuses each transfer, and how much previous work the
server can keep. MoE gives us sparse computation. The rest is arranging the
memory around it.
