# EmberVM brick-program decisions (autonomous run log)

Running log of decisions made during the autonomous brick-model implementation. Fable is the decision-maker for forks encountered mid-run; Joe is escalated only when Fable is stuck or needs him. Formal architecture rationale lives in the ADRs (docs/decisions/embervm/); this file is the lightweight running log.

## 2026-07-19

- **Capacity model: bricks everywhere, drop in-place resize.** Fixed-size T-shirt bricks are the single capacity unit on both tiers; the control plane moves per-size-class counts, kube-scheduler bin-packs them. A Pending brick is the fleet-full signal (Karpenter adds a node on EKS; refuse placement and page on the fixed homelab). Recorded in ADR 012/013 (amended, PR #3720). In-place resize (PR-I, draft #3715) shelved. Decider: Joe.
- **Cutover shape: both size-classes at once.** The DaemonSet to brick cutover ships small and large together (node-4 already runs serving/session workloads needing a large brick). Decider: Joe.
- **Instance identity: pod_uid.** Registry and ledger keyed by the kubelet pod UID; retires the seed's control-plane-issued instance_id anchor. Decider: Joe.
- **Scratch disk: generic logical path (Option B).** noded scratch path renamed from the device-specific /disks/nvme-02 to /var/lib/embervm/scratch; operators bind-mount each node's real device there. Tier-portable (matches Karpenter instanceStorePolicy RAID0 on EKS). Decider: Joe.
- **Brick-count controller location: inside the brick capacity PR**, not R0 PR-3 (single writer plus the Deployments it scales is one review and rollback unit). Decider: Fable.
- **Scratch mechanism: hostPath as a node-provisioning contract; local PV rejected after re-examination.** The generic logical path (/var/lib/embervm/scratch, Option B) stands, but who creates it is now decided: node bootstrap owns the mapping from real device to logical path. Karpenter userData on EKS; a scratch-prep DaemonSet (ConfigMap node map, idempotent bind-mount plus fstab) on the homelab. local-static-provisioner PVs rejected: PVC exclusivity fights the node-scoped shared cache (surge handover, shared baked rootfs), clean-on-release restores the fetch tax, and static local PVs fight Karpenter scale-up. ADR 012 storage bullet amended. Outage note: node-4 restored by bind-mounting /disks/nvme-02 onto the logical path, reusing existing baked artifacts. Supersedes the bare "operators bind-mount" clause of the Option B entry. Decider: Fable (ratified in the live session).

- **Per-instance scratch dirs move OUT of PR-1 to PR-3 (Option B).** The 3-PR brick split as originally designed put `instances/<pod_uid>/` per-instance warmth dirs in the inert PR-1. On implementation review this was pulled forward to PR-3: the collision per-instance dirs prevent (two co-located bricks clobbering each other's warmth) cannot physically occur until PR-3 introduces co-location, so landing the split in PR-1 buys zero protection while parking a ~15-call-site refactor of the driver's snapshot root (bases/ must stay node-shared while sessions/serving/stateful/group/threads/checkpoints go per-instance) unexercised for two PRs. That warmth-critical, CI-only-verifiable path is the same area whose path skew caused the demo-postgres 503, so "inert because no pod triggers it" is strictly worse than "exercised the moment it lands behind the PR-3 1-small+1-large canary." Durable data is already isolated on the separate node-shared VolumeRoot, so the deferred risk is bounded to regenerable warmth, never data. Escape hatch if the PR-3 diff grows: carve a mechanical PR-2.5 for the root-split immediately before PR-3 (never back into PR-1), and never apply the split unconditionally to the live DS (repathing its existing tree cold-starts live warmth for no benefit). PR-1's concrete scope is therefore proto `NodeStatus.size_class=30`, noded `EMBERVM_NODED_SIZE_CLASS` plumbed to NodeStatus (not used for pathing), chart brick Deployment templates behind `bricks.enabled=false`, and `Embervm.BrickLedger` populated-but-unread; the DS rolls once with no path or behavior change. Decider: Fable.

- **PR-2 placement rewrite is minimal and dispatcher-only (Option B).** A read-only map of the placement surface showed the original "rewrite every consumer through pick_brick" is over-scoped: the multi-brick-collapse bug (`prefer_newest_per_node`, which keeps only the newest INSTANCE per node) lives in exactly ONE place, `dispatcher.ex` (call + definition). Session and serving placement use rendezvous-hash over per-instance facts, which already spreads across co-located bricks; stateful is volume-anchored and group is node-anchored, so neither selects among instances. So PR-2 = dispatcher only: delete `prefer_newest_per_node` (call + definition + comment) and replace the warm-tier and miss-tier tie-breaking (today's arbitrary-order `Enum.find`) with `BrickLedger`'s deterministic sticky-hash selection, while keeping warm-vs-miss as the dispatcher's own two-tier logic (warmth is inventory/prime-budget knowledge, not capacity accounting, so `BrickLedger` stays warmth-agnostic). Session/serving/stateful/group and the instance_id-vs-node_id keying inconsistency are untouched (keying unification is deferred to its own mechanical PR; node-scoped snapshot reads stay valid regardless). Land now while the fleet is DS-only: on one-instance-per-node both the collapse removal and the sticky tie-break are output-equivalent (one candidate per node either way), so PR-2 soaks on live dispatch traffic with zero behavior change before PR-3 turns on co-location, and puts PR-1's ledger live. Accepted trade: `prefer_newest_per_node` also covered the seconds-wide surge-roll window (old pod + fresh replacement briefly coexisting); since draining rows are already dropped fail-closed, removing it accepts a rare, self-healing chance of placing on a pod about to drain, which is correct under bricks where a node legitimately holds several instances. Decider: Fable.

- **PR-3 split 3-way (3a mechanism / 3b canary / 3c prune); values-knob desired counts; DS-prune gated on Joe.** PR-3a lands `Embervm.BrickController` (singleton GenServer, single writer, started AFTER Finch in the supervision tree so the known CP-boot Finch-ordering bug never shares a diff with a live cutover) + `K8s.scale_deployment/3` + RBAC (Role: deployments/scale get+patch, deployments get, embervm ns) + terminal `:fleet_full` (desired>registered for 5m -> 503 + telemetry), all inert behind `bricks.enabled=false`. Desired counts come from a per-class `desiredReplicas` values knob rendered into CP config that the controller reconciles to `/scale` (computed demand deferred; ArgoCD's fleet-wide ignoreDifferences on /spec/replicas means git-declared replicas would not sync anyway, so routing the number through the controller both solves that and exercises the reconcile loop). PR-3b is the one-line `bricks.enabled=true` canary flip on the $values git ref (no chart bump), staged small-first (small=1, large=0; verify; then large=1) so node-4 never absorbs the full +3-core request spike at once during the DS overlap; this is the first real co-location and first exercise of PR-2 dispatcher spread + PR-2.5 per-instance warmth. Between 3b and 3c: verify both bricks dial-home registered with correct size_class, dispatch landing on bricks via BrickLedger.choose, per-instance warmth dirs created with no cross-clobber, no spurious :fleet_full, CP stable, one deliberate demo-postgres exercise; soak a few hours past the 5m fleet-full window. PR-3c is the one-line `noded.enabled=false` DS prune, irreversible-ish (rollback = re-enable the DS, which cold-starts warmth), so it is GATED ON an explicit Joe go-ahead with soak evidence, and forces a StatefulManager.wake for demo-postgres immediately after (the prune kills its host instance). 3a and 3b proceed autonomously (both cheaply reversible: 3b reverts by bricks.enabled=false). 3a's chart bump rolls the DS noded; only a postgres-guest-image-tag change actually rebuilds the demo-postgres base and wedges it (task #21), so budget a forced wake only if that fires. Decider: Fable.
