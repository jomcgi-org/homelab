# Writing for human readers

Rules for everything people and agents write here: docs, `ARCHITECTURE.md`
and STPA prose, runbooks, PR bodies, commit messages, issue and PR comments,
itsaplan tickets, chat replies, jomcgi.dev page copy and engineering posts.
Simple and easy to digest beats dense and complete. Higher signal comes from
cutting, not compressing.

The hard bans apply to everything written in this repo, including commit
messages and PR bodies. The voice rules apply to any prose a human will
read. Simplified Technical English and diagrams apply to everything except
public page copy, where "Know the reader" comes first. "Know the reader" is about matching the register to the audience.
Site copy and posts speak in first person about Joe's work, so the
self-praise and self-rating rules bite hardest there. For site copy and CV
prose, audit facts and flag unsupported claims, but offer at most one draft:
Joe writes the final wording.

## Know the reader

Two audiences, two registers.

**Public pages** (jomcgi.dev, `/ember/*`, demo pages). Visitors skim, and
many are not infrastructure engineers. Print the meaning of a mechanism;
keep the mechanics for deep docs. Translate jargon a skimming reader
bounces off ("no network card" over "no NIC"). The user-facing capability
is the hook; how it is built comes second or gets cut. Example of the
register: "the egress sidecar makes the call and attaches the real token;
the secret never enters the VM" carries the meaning without the
certificate-issuance mechanics.

**Repo docs** (READMEs, `ARCHITECTURE.md`, runbooks). Readers
are engineers, including future maintainers and agents. Mechanics belong
here: exact resource names, ports, verbs, file paths. The voice rules
below still apply in full.

## Hard bans (AI-tell rhetoric)

- **No em-dashes.** Anywhere. Use a comma, colon, parentheses, or split
  the sentence. Existing ones are grandfathered: never churn a file just
  to strip them, but remove them from any prose you are rewriting anyway.
- **No "not X, but Y" antithesis** ("a design input, not a postmortem").
  State the positive claim and stop.
- **No arrow chains in prose** ("weeks -> minutes",
  "measure -> detect -> cap"). Write the words.
- **No decorative rule-of-three.** Keep a list only when every item is
  real evidence; otherwise one strong point.
- **Banned vocabulary**: "load-bearing" (total ban), "clean-sheet" (say
  "built from scratch" or name the language), "making the hard path the
  easy one", "center of gravity". If a phrase is frequently generated by
  AI tools, it is out.

## Simplified Technical English

Follow about 80% of
[ASD-STE100 Simplified Technical English](https://asd-ste100.org/about_STE.html)
(STE), the controlled language of aircraft maintenance manuals. STE text
reads the same way for every reader, including a program. Keep its writing
rules. Skip its approved dictionary, because our text is mostly technical
names and technical verbs.

- A sentence has 25 words or fewer. An instruction, such as a rollback
  step, has 20 or fewer.
- One topic in each sentence, and one action in each instruction. Put a
  condition first: "If the probe fails, lower the pin to 0.29.10."
- Active voice, with the actor named: "the connector rewrites the body".
- Simple tenses. Use the present for what the code does and the simple past
  for what happened or ran. Do not use the present perfect ("has fixed").
- Noun clusters of three words or fewer. A code identifier counts as one
  word.
- One word for one thing. Use the repository's names (`connector`,
  `coder`, `reviewer`, `HOME-N`) and keep each one through the text.
- Specific words: a count, a time or a name, over "some", "several" or
  "quickly".
- Prose keeps its articles and verbs. A bullet keyed by a path can be a
  fragment.

Code, commands, identifiers, quoted log lines and links are outside these
rules.

## Diagrams

A diagram replaces paragraphs. Draw one for a request flow, a trust
boundary, a state machine or ownership between components, and delete the
prose it replaces. Skip it for a one-component change or a version bump.

- Use Mermaid where GitHub renders it: docs, PR bodies and comments. In a
  terminal chat, draw a small text diagram in a code block.
- Show only the path that matters, in about 12 nodes or fewer.
- Label edges with the verb, protocol or condition.
- `sequenceDiagram` for calls between services, `stateDiagram-v2` for
  states and transitions, `flowchart LR` for data flow and ownership.
- Use basic syntax. GitHub's Mermaid version decides what renders, and the
  source should read well as text.
- A diagram is a claim like any sentence. It must match the code.

## READMEs and architecture documents

Each file answers one question. Text that answers a different question moves
to the file that owns it.

| File | Answers | Leaves out |
| --- | --- | --- |
| Root `README.md` | What the factory is, how a change ships, where things run today and the direction | Mechanics, versions and model names |
| `projects/<domain>/ARCHITECTURE.md` | How the domain works now, why, and what is decided next | Operator steps, rollout checklists, PR history |
| `projects/<name>/README.md` | How to operate it: commands, inputs, recovery steps | Design rationale |
| HOME issue | Rollout steps, acceptance checks, open questions | |

An `ARCHITECTURE.md` has these parts, in this order:

1. **Summary.** Five sentences or fewer, then one diagram of the components
   and the main flow. A reader who stops here knows what the domain does.
2. **Current state.** One section for each component. Write what runs now, in
   the present tense. Draw each flow, state machine and trust boundary. End a
   section with a `**Why.**` paragraph that links the decision.
3. **Direction.** One table: direction, HOME issue, state. Staged-off work is
   a row here. A row leaves the table when the work ships or its issue closes.
4. **Decision history.** Links to the decision records.

Keep the file current by replacing text:

- When work ships, rewrite the section and delete the Direction row.
- Delete a dated status line, a delivery plan or a bootstrap note when its
  work completes. `git log` and the HOME issue keep the history.
- Put a pinned version in one table. Do not repeat it in prose.
- Put upstream findings that shaped the design in a `**Why.**` paragraph or an
  appendix, after the current state.
- A section longer than 60 lines needs a diagram or a split. A file longer
  than 600 lines moves a component into its own file and links it from the
  summary.

Files written before 2026-11-18 follow these rules when someone rewrites a
section.

## Voice

- **No connective glue.** Cut phrases that narrate a structure before
  showing it ("with a clean ownership boundary:", "which means that",
  "notably"). A semicolon split does the work; when in doubt, two blunt
  sentences.
- **No consequence narration.** After stating facts or a mechanism, stop.
  Never append a clause explaining what the facts add up to ("grant
  access once and it is correct everywhere"). The reader gets it.
- **No self-praise.** No quality adjectives about one's own work
  ("clean", "robust", "elegant"). Show the scope, the number, the
  boundary, and let it land.
- **No self-rating labels.** Never label your own role ("owned it
  end-to-end" fails "would you say that out loud to another engineer?").
  Name the initiating act ("Found the gap") and let the verbs carry it;
  the reader concludes ownership.
- **No reviewer labels.** Never introduce evidence with an editorial
  label: "the sharpest case", "most notably", "the killer example",
  "crucially". That is a critic's voice narrating significance. State
  the case and end on the fact.
- **No thesis or aphorism openers.** "Most of platform engineering is
  detection" is thought-leader material. Open with what the thing is or
  does; hang evidence off that.
- **No costume nouns.** Name the literal actor instead of dressing a
  fact in security vocabulary. "My friends have been trying to pull keys
  and exfiltrate data from it since day one. None have managed it."
  beats "The same red team has been trying since day one." The costume
  is exaggeration; the bare fact is stronger.
- **Capability over artifact.** Describe what a thing enables, not what
  was built ("a Svelte frontend" is noise; "apps that sleep when idle
  and wake when called" is the hook).
- **Prose is sentences, not inventory.** Each sentence explains itself
  ("stateful apps and databases that sleep when idle and wake when
  called"); a paragraph or bullet past ~200 words is a wall. Prefer
  replacement over growth: new evidence pays its way by displacing
  weaker detail.
- **Reuse Joe's literal nouns.** His word over a synonym ("process",
  not "machinery"); real repo names over cute coinages.
- **Cut, don't compress.** More impact with less content means deleting
  a clause, not squeezing it into denser phrasing.
- **Headings are outcome-led and short**, never mechanism-led catalogs.
- **The best lines are short dry standalone declaratives** ("A new
  source is one proto schema."). Check every sentence against "does this
  sound like Joe?".

## Formal analysis reads as an outcome

Lead with what the analysis found, and let the findings say why the
method was worth running. "An STPA hazard analysis of the shipped code
found two trust-boundary holes I hadn't documented, both on the
remediation roadmap" is the register to copy for STPA and TLA+
material.

## Checklist before publishing

Grep the draft for the common violations:

- em-dashes, and `->` in prose
- "not just", "isn't just"
- "sharpest", "most notably", "crucially", "killer"
- "load-bearing", "center of gravity", "clean-sheet", "making the hard
  path the easy one"
- "clean", "robust", "elegant" applied to one's own work
- "red team" where the literal actor is friends

The grep catches the vocabulary, never the shapes: antithesis,
consequence narration, and reviewer labels only show up on a read.

Then read it once asking only: does every sentence sound like Joe, and
does every clause earn its place?
