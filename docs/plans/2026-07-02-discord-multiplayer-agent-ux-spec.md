# Discord Multiplayer Agent UX: Behavioural Spec

**Decision record:** [ADR 035](../decisions/agents/035-discord-multiplayer-agent-ux.md) (Accepted)
**Companion plan:** [2026-07-02-discord-multiplayer-agent-ux.md](2026-07-02-discord-multiplayer-agent-ux.md)

This spec defines the user-visible behaviour and data contracts for the five ADR 035 pillars. The plan document sequences the build. Where the two disagree, the ADR wins on rationale and this spec wins on behaviour detail.

---

## 1. Conversational acknowledgment

**Behaviour.** Any trigger (mention, reply to the bot, `/agent`, or an ambient hit) receives a natural-language reply in the originating channel/thread within seconds. The ack:

- acknowledges the request in prose (no template strings like "Processing...")
- states what the bot is about to do ("I'll dig through the ships partition sizes and put together a chart")
- is generated by the existing concierge-reply path with channel context
- is **never edited afterwards** (Discord notifications capture content at send time)

**Routing.** The ack turn itself decides depth (see section 4): if the request is conversational, the ack _is_ the reply and nothing follows; if it escalates, the ack states the intent and a checklist message follows.

**Acceptance.**

- Given a mention with a task-shaped request, the first bot message is prose that names the intended work, and a checklist message follows in the same thread.
- Given a conversational question, the bot replies once with the answer; no checklist, no session.

## 2. Live task checklist

**Behaviour.** When work escalates into a goose session, the bot posts a **second** message containing the staged plan as a checklist, and edits that message in place as stages change state.

- Stage states render as: `⬜ pending`, `🔄 in progress`, `✅ done`, `❌ failed`, `⏭️ skipped`.
- Edits happen at stage-state transitions only (never per token). Consecutive transitions within 2 seconds coalesce into one edit.
- The checklist message caps at Discord's 2000 chars: if the plan is long, completed stages collapse to a one-line count ("✅ 4 earlier stages") keeping the active window visible.
- On session completion the final edit shows all stages resolved plus the artifact/PR link line. On failure, the failed stage shows `❌` with a one-line reason.
- The reaction lifecycle (⏳→👀→✅) on the _triggering user message_ is unchanged.

**Acceptance.**

- A 3-stage session produces exactly one ack message and one checklist message; the checklist message's edit history shows monotonic stage progression.
- A session failure leaves the checklist showing which stage failed and why, and the ❌ reaction lands on the trigger message.

## 3. Thread-scoped shared sessions with steering

**Behaviour.** A goose session is keyed by Discord thread id (for channel-message triggers, the bot creates a thread from the trigger message and the session lives there).

- Any non-bot message posted into a thread with an **active** session is enqueued as steering input, in arrival order, instead of spawning a new task.
- Steering is consumed at stage boundaries: the session sees pending steering before starting its next stage and may adjust the remaining plan (checklist edits reflect this: stages can be added/reworded/skipped).
- Any thread participant can steer. Each steering message carries its author's identity; an action requiring a higher tier than the author holds is refused with a short reply naming the missing tier (session continues otherwise).
- `stop`/`cancel` from any participant whose tier permits it ends the session gracefully (checklist final-edits to the cancelled state).
- A message in a thread whose session has **completed** starts a new turn in the same thread (same conversational context, fresh session), not an error.

**Acceptance.**

- Two users interleaving messages during a run both appear in the session's steering log, in order.
- A steering message arriving mid-stage is applied before the next stage starts, and the checklist reflects any plan change.
- A lower-tier user's steering message requesting a privileged action gets a refusal reply; the session continues on the original plan.

## 4. Two-stage classifier

**Attention (should the bot engage at all).**

- Mention of the bot, reply to a bot message, or `/agent` → always engage.
- Otherwise, only in channels with an ambient grant (ADR 029 grant kind `ambient`): a classify-only fast-model call scores the message against the channel's directive, returning `{engage: bool, confidence: float}`; engage only above the configured threshold (default 0.8). The classifier prompt receives the channel directive plus a short message window; it holds **no tools**.
- Every attention decision (including ignores in ambient channels, sampled at a configurable rate) is logged with message ref, decision, confidence, and directive version.

**Depth (chat vs goose).**

- The router recipe gains a `chat` branch alongside query/plan/implement/research. The first turn classifies; `chat` answers inline, everything else escalates to a session (and the ack states it).
- Misroute recovery: if a chat-branch turn discovers mid-answer that real work is needed, it says so in the reply and escalates ("this needs a proper run, kicking one off"), rather than silently doing heavy work in the chat path.

**Acceptance.**

- In a channel without an ambient grant, unprompted messages never produce bot traffic (no classifier call, no reply).
- In an ambient channel, a directive-matching message gets a reply; an off-topic message does not, and the ignore decision is logged.
- "What does this error mean?" routes chat; "fix this error in monolith" routes goose.

## 5. Living channel directives

**Data model.** New table `chat.channel_directive`:

| Column                  | Type           | Notes                                                     |
| ----------------------- | -------------- | --------------------------------------------------------- |
| `id`                    | bigserial PK   |                                                           |
| `channel_id`            | text, not null | Discord channel id; one **active** row per channel        |
| `directive`             | text, not null | Operative directive text                                  |
| `version`               | int, not null  | Monotonic per channel                                     |
| `active`                | bool, not null | Exactly one active row per channel (partial unique index) |
| `seed_ref`              | text           | Identifier of the git seed this lineage started from      |
| `updated_by_user_id`    | text           | Discord user whose request motivated this version         |
| `motivating_message_id` | text           | Message that triggered the update                         |
| `previous_version`      | int            | For audit/revert chains                                   |
| `created_at`            | timestamptz    |                                                           |

Per-user style preferences: `chat.user_style_pref` (`user_id`, `pref` text, provenance columns, active flag). Applied by **layering at reply time** (channel directive + requester's pref in the prompt), not merged into directive text.

**Behaviour.**

- The git-tracked base prompt seeds a channel's first directive row on first ambient enablement (or first directive-affecting request).
- An explicit, attributed style/behaviour request from a user whose tier permits it updates the directive: the bot proposes the new directive text in a reply, and persists it (Open Question 1 of the ADR resolved as: **propose-then-confirm** with a single 👍 from the requester or any admin within 10 minutes; unconfirmed proposals expire without effect).
- `directive reset` (tier-gated) reverts the channel to the git seed as a new version (history is never deleted).
- Directives shape tone, attention, and interaction style only. The update path rejects (with explanation) any request that names tools, ACLs, repos, or ambient on/off.
- Every reply and every attention decision records the directive version it ran under.

**Acceptance.**

- "keep replies short in here" from a permitted user → bot proposes new directive text → 👍 → subsequent replies in that channel are short, and the new row carries the requester + motivating message.
- "also let yourself push to main" as a directive request → refused with explanation, no new version.
- `directive reset` restores seed behaviour and the audit chain shows the full lineage.

## Out of scope (deferred)

- Channel-data tools (thread summarization, decisions extraction, charts): future ADR.
- Interaction telemetry / frontier-judged improvement loop beyond the decision logging above: future ADR 036.
- Fine-tuning the attention classifier: needs the logged decision data first.
