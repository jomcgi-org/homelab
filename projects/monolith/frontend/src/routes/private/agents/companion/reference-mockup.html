The voice companion

A parallel surface that a voice session grabs over MCP. The voice model holds the remote: it conjures the run DAG, the walkthrough, or a decision onto the stage, runs the session tools out loud, and the stage holds only what the conversation is about right now. Same material as /private/agents, one new idea: the screen follows the talk.

What changed in rev 2

  • The walkthrough card now mirrors the console's new full-page walkthrough: the agent's account reads first as prose, then the file and its counts, then the diff, and files changed without explanation are named in a register rather than dropped. The provenance banner and point counts rev 1 carried are gone because the console stripped them as bookkeeping.
  • Decay is engine behavior now, not staged frames: every beat only declares what the conversation references, and the stage works out what recedes, what leaves, and what gets re-summoned. The pin control on every card is live; try pinning the walkthrough at beat 3 and watching it survive the rest of the conversation.
  • Tooling by voice: beat 4 runs semgrep from a spoken sentence. The call goes down the session lane, surfaces itself as an ephemeral tool card with no voice_ui_show involved, and resolves live on the stage.

How to read this

Press play, or step with the arrows. Each beat is one exchange in a voice conversation: what you said, what the model spoke back (the <voice> line it already emits per turn), and the calls it made to move the stage. The wire at the bottom is deliberate: every surface names the call that summoned it, so the fluid behavior never becomes unaccountable. At beat 6 the decision gate is answered by voice, but the buttons on the card resolve the same gate; both channels are peers.

Surface lifecycle

Relevance is the only layout rule. A surface is front while the conversation references it, recedes when it goes one exchange without a mention, and leaves after two. Tool runs are more ephemeral than views: they skip the receded stop and leave after one. Anything can be re-summoned, and it arrives fresh.

state enters when leaves how
front conjured, or re-referenced by the current exchange goes unreferenced for an exchange
receded · 50% one exchange since last reference re-reference restores front; a second quiet exchange removes it
gone two quiet exchanges; one for tool runs only a fresh summon brings it back
pinned you press pin you unpin or dismiss; the model's show and dismiss cannot touch it

Proposed tool surface

Four tools alongside the existing monolith_agent_session_* family. All return on accept, in the session-lane style. If no companion is open, every call is accepted and does nothing: voice must work with the screen off.

tool shape behavior
voice_ui_attach {session_id} Binds any open companion to the session. Populates identity: model, vm state (from the CP listing, not session columns), repo, branch. The caller passes the session id explicitly; MCP calls carry no real actor identity today, so the companion cannot infer "my session".
voice_ui_show {surface, ref, focus?} Conjures a surface: run, walkthrough, transcript, vm. Whatever it displaces starts decaying rather than being cleared. focus targets a node, a turn, or a file in the walkthrough.
voice_ui_ask {question, options, ref} Raises a decision card. Returns accepted immediately; the answer (spoken or clicked) is delivered back through the existing agent_session_send path as the next message, so the voice turn never blocks on the screen.
voice_ui_dismiss {surface?} Clears one surface or the stage. The user's own pin and dismiss controls always outrank the model's.

Tooling by voice

The remote is not read-only. The voice lane already reaches the session tools over MCP; the change is that a companion, when open, renders each call as an ephemeral surface instead of leaving it buried in a transcript. Nothing new is minted for this: the wire is the source of truth and the card is just its view, which is why beat 4 shows no voice_ui_show before the semgrep card appears.

call status what the companion shows
agent_session_send real the resolution path for asks and send-backs (beat 6)
semgrep_scan real a tool run card: args while running, findings when done (beat 4)
agent_trigger_job, k8s reads real the same tool card shape
auto-surfacing of wire calls proposed the behavior itself: calls become cards, cards decay fastest

Authorization stance for review: reads and session-lane sends run on voice alone. Anything that mutates outside the attached session raises voice_ui_ask first and waits for the word or the click.

Principles

  • Visible strings. Every surface carries its summoning call, and the wire logs the full sequence, including calls that are not voice_ui_* at all. Fluid, never inexplicable.
  • The user outranks the model. Pin freezes a surface against show and dismiss; the close control always works. Both are live in this mockup.
  • Surfaces decay. One quiet exchange recedes a surface, two remove it, and tool runs get one. The stage holds at most what the conversation is about, not a dashboard's worth of state.
  • The wire is two-way. The companion is a remote that reads and acts: session tools run on a spoken sentence, and the ask gate is the boundary before anything heavier.
  • Mirrors, not forks. Cards are read-only remounts of console pieces (staged DAG, walkthrough, transcript) and deep-link into /private/agents for anything heavier than a glance.
  • Degrade to voice. Companion closed means the tools no-op. Nothing in the voice flow may depend on the screen being up.

Real vs proposed

  • real The spoken line: voice.py already stores a <voice> summary per turn and agent_session_status returns it.
  • real The staged DAG, vm chip semantics, and the theme tokens are lifted from RunView and agents-theme.css as they ship today.
  • real The walkthrough anatomy matches WalkthroughNarrative as of 2026-08-15: a finished session opens on the full-page walkthrough, the account reads before the diff, and "Changed without explanation:" names the files the agent never mentioned, which is the case the feature exists to surface.
  • real semgrep_scan, agent_session_send, and agent_trigger_job exist on the MCP path today; beat 4 invents nothing about the call, only about its rendering.
  • proposed The four voice_ui_* tools, the lifecycle and pin behavior, auto-surfacing of wire calls, and ask resolving through the session-send path.
  • proposed Beat 6 shows send-back queuing a third implement attempt. That is the direction for the reviewer loop (the plan gains an attempt), not current behavior: today a request-changes verdict ends the run.

Open questions

  • Attach identity: is speaking the session id acceptable, or does this wait for caller identity on the MCP path? Nothing on that path carries a real actor today.
  • Transport: the console is poll-shaped by decision; the companion wants push. Reuse the vms/stream SSE pattern, or accept a short poll?
  • One companion per session, or a grabbable wall surface where the latest attach wins? Needs a contention rule either way.
  • Does the wire ledger persist with the session (auditable) or live only in the companion (ephemeral)?
  • Voice-invoked tooling: is call-on-voice right for reads and session sends, with voice_ui_ask gating anything heavier, and which named tools sit on each side of that line? Feels like the ADR's job to enumerate.
